= AI Governor Architecture — exchangeable building blocks
:author: deepseek-v4.1-flash
:date: 2026-09-26
:status: proposal
:scope: src/game/engine/AI/*, src/game/engine/AutoProduction.ts

This document proposes how to turn the current monolithic AI into a
utility-based blackboard AI whose behaviour is assembled from small,
exchangeable policy blocks and situation-dependent "governors". It covers the
current state, the diagnosis, the target architecture, a migration plan, and an
honest assessment of the trade-offs.

== 1. Current state (what the AI is today)

The building pieces already exist, but they are wired as a monolith:

* `AIManager.runAITurn` (`src/game/engine/AI/AIManager.ts:197-924`) is the whole
  civ brain: strategy, research, government, diplomacy, war, missions,
  per-unit movement, then production.
* `chooseAITarget` (`AIManager.ts:1692-2265`) is a 574-line `if` chain.
* `AutoProduction.determineProductionItem`
  (`src/game/engine/AutoProduction.ts:237-706`) is a 470-line first-match
  ladder in which **order is policy** (defense > island > mission > fisher >
  happiness > ...).
* Situations are implicit conditionals scattered across modules: island and
  coastal checks, `netThreat`, `isAlone`, at-war, map type. The same situation
  is recomputed in three to five places (threat assessment, "unhappy"
  predicate, `sustainableUnits`, difficulty tables, unit strength formulas).
* The dynamic strategy layer is effectively dead: `AIStrategySelector` runs
  every 10 rounds, but `resolveAICivStrategy`
  (`src/game/engine/AI/AITypes.ts:148-153`) always prefers the fixed
  `civ.productionProfile`, so every consumer ignores the re-evaluation.
* AI cities use a fixed governor profile
  (`src/game/engine/AI/AICityManager.ts:142-151`) while human cities get the
  parameterised `GOVERNOR_PROFILES` (`AICityManager.ts:94-139`).
* Colony and invasion missions are the closest thing to the desired model:
  explicit `gather -> sail -> siege` state machines
  (`AIManager.ts:1128-1372`), but implemented as private methods and shared
  `turnData` keys written by `AIManager` and read by `AutoProduction`.

Reusable situational API already available on the engine
(`src/game/engine/GameEngine.ts:1837-2050`): `getIslandSituation`,
`getColonizableIslands`, `getLandmassId` / `areLandConnected`,
`civHasCoastalCity`, `civHasNavalCity`, `civCanBuildShips`, `civNeedsNavy`,
`hasSeaInvasionTarget` (in `AIManager`), plus the ferry and fishing primitives.

== 2. Diagnosis — strengths and weaknesses

=== 2.1 Strengths to preserve

* Per-civ identity via `StrategyProfile` and `getCivPersonality`.
* Mission state machines are correct, small, and covered by tests
  (`tests/ai/aiNavalInvasion.test.ts`, `tests/ai/aiIslandStrategy.test.ts`).
* A real situational query surface now exists on `GameEngine`.
* The test suite (39 AI test files) plus the headless session scripts
  (`scripts/run-naval-session.mjs`, `tests/ai/tmpNavalSession.test.ts`) give
  regression safety.

=== 2.2 Weaknesses that block situational flexibility

. **Ordering-as-policy.** Adding a situation means inserting another branch in
  two giant methods. It is impossible to express two responses at once, e.g.
  defending an island *and* invading elsewhere.
. **No shared situation model.** Every module asks its own questions with its
  own thresholds, which is why adaptivity is inconsistent.
. **One blackboard, five writers.** `turnData` (`aiState`, `offensivePlan`,
  `colonyMission`, `invasionMission`) is written by `AIManager` and
  read/mutated by `AutoProduction`, which is itself invoked from five call
  sites. No owner, no schema.
. **Identity and situation are conflated.** A civ is either
  `defensive_turtle` or `military_expansion`; there is no stable identity that
  overlays a situational posture (small raid vs. full invasion).
. **Dead and duplicated tuning knobs.** `isBorderCity` is never true,
  `EconomicManager.AI_MIN_GOLD_RESERVE` is never assigned, two difficulty
  tables exist, two `sustainableUnits` models exist.

== 3. Target architecture — the ideal system

Utility-based blackboard AI with data-composed governors. This is not a rewrite:
it is an extraction plus one new layer. Three stable layers, one arbiter, one
execution adapter.

=== 3.1 Layer 0 — `WorldView` (read-only, built once per turn)

One shared snapshot replaces `buildGameState`
(`AIManager.ts:4184-4298`, `AutoProduction.ts:1415-1465`) and the inline
snapshot in `TurnManager`: own cities/units/economy/tech, fog-limited enemy
knowledge, geography (landmass graph, island situation, naval relevance).

[source,typescript]
----
interface WorldView {
  civId: number;
  round: number;
  civ: { techs: Set<string>; gold: number; profile: StrategyProfile; personality: Personality };
  cities: OwnCityView[];
  units: OwnUnitView[];
  knownEnemies: { locations: EnemyLocation[]; cities: CityView[];
                  visibility: 'visible' | 'stale' };
  geography: { landmassCount: number; ownLandmass: LandmassInfo | null;
               islands: ColonizableIsland[]; navalRelevance: number };
  economy: { income: number; expenses: number; sustainableUnits: number;
             unitCapHeadroom: number };
}
----

=== 3.2 Layer 1 — `SituationReport` (the missing piece)

A pure function `WorldView -> SituationReport` that turns scattered
conditionals into typed, testable data.

[source,typescript]
----
interface SituationReport {
  posture: 'peace' | 'defensive' | 'offensive' | 'emergency';
  geography: { kind: 'landlocked' | 'single_landmass' | 'small_island'
                    | 'archipelago' | 'split_empire';
               isAlone: boolean; size: number };
  threats: CityThreat[];        // per city: severity + classification
  economy: { goldCrisis: boolean; famine: boolean; unhappy: boolean;
             capHeadroom: number };
  opportunities: { colonizableIsland: boolean; seaInvasionTarget: boolean;
                   wonderRace: boolean };
}

interface CityThreat {
  cityId: string;
  netThreat: number;
  kind: 'none' | 'raid' | 'landing' | 'invasion' | 'main_force';
  closest: { col: number; row: number; distance: number };
}
----

`kind` classification is the key addition: today `netThreat >= 2.5`
(`AIManager.ts:3671-3683`) cannot distinguish "three barbarians landed" from
"the enemy main army is coming". `raid` triggers local response, `main_force`
triggers plan cancellation and mobilisation.

=== 3.3 Layer 2 — policy blocks (pure, side-effect-free)

One idea per block. Blocks never touch the engine; they only read the world
view and the situation and emit scored proposals.

[source,typescript]
----
type Domain = 'production' | 'labor' | 'economy' | 'research'
            | 'military' | 'naval' | 'expansion' | 'diplomacy';

interface Proposal {
  domain: Domain;
  action: unknown;              // discriminated union per domain
  target?: { col: number; row: number } | string;
  score: number;
  reason: string;               // human-readable, logged
  constraint?: boolean;         // hard gate, cannot be outvoted
}

interface PolicyBlock {
  id: string;
  domain: Domain;
  applies(w: WorldView, s: SituationReport): boolean;
  propose(w: WorldView, s: SituationReport): Proposal[];
}
----

Candidate blocks (mapping the current branches):

[cols="1,2",options="header"]
|===
| Block | Replaces / covers
| `ThreatDefense` | threat-first defender production and garrison
| `RaidResponse` | *new*: small-group landing response
| `IslandEscape` | very small island -> ferry/warship first
| `Colony` | `updateColonyMission` / `tryColonyFerryAction`
| `NavalInvasion` | `planInvasionMission` / `tryInvasionFerryAction`
| `Blockade` | `chooseNavalTarget` blockade branch
| `FleetProduction` | `buildNavalProduction`, navy pivot
| `Expansion` | settler cadence (`EXPANSION_PARAMS`)
| `Growth` | granary/aqueduct/food security
| `Happiness` | temple/colosseum/cathedral, entertainers
| `Building` | `AIBuildingStrategy.evaluateBuildings`
| `Wonder` | `AIBuildingStrategy.evaluateWonders`
| `TaxPolicy` | `AIEconomicManager.adjustRatesForAI`
| `Labor` | `AICityManager` tile swaps and specialists
| `Research` | `AIResearch.selectResearch`
| `ScoutCorps` | scout caps, exploration targets
| `Diplomat` | diplomat production and actions
| `WarPosture` | `AIAggression.computeAggression`, bulk attack plan
|===

=== 3.4 Layer 3 — governors are data, not code

[source,typescript]
----
interface GovernorSpec {
  id: string;
  blocks: Array<{ block: string; weight: number }>;
  slots: Domain[];               // decision slots this governor owns
}

interface SituationDirector {
  select(w: WorldView, s: SituationReport): GovernorSpec[];
}
----

A `SituationDirector` maps situation flags to active governors; governors
stack per civ, per city, and per fleet. Examples:

[source,typescript]
----
const NavalGovernor = {
  id: 'naval',
  blocks: [
    { block: 'threat_defense',  weight: 1.5 },
    { block: 'naval_invasion',  weight: 2.0 },
    { block: 'blockade',        weight: 1.0 },
    { block: 'fleet_production', weight: 1.8 },
  ],
  slots: ['naval', 'production'],
};

const IslandDefenseGovernor = {
  id: 'island_defense',
  blocks: [
    { block: 'threat_defense', weight: 2.0 },
    { block: 'raid_response',  weight: 2.5 },
    { block: 'island_escape',  weight: 0.7 }, // applies only if verySmall
  ],
  slots: ['production', 'military'],
};
----

Same blocks, different mixes — that is the requested "not a fixed set of
governors, but the result of blocks pulled together", while remaining
debuggable and reproducible.

=== 3.5 Layer 4 — arbiter

For each decision slot:

. Collect proposals from active governors (weight multiplied into `score`).
. Apply hard constraints (`constraint: true` wins; e.g. a threatened city must
   not build a wonder — today enforced implicitly by branch order).
. Apply hysteresis: the incumbent decision must be beaten by a configurable
   margin. This generalises the existing plan-age and rally-timeout stickiness.
. Pick the winner; emit a decision-log entry with score and reason.

Decision slots include: production item per city, labour assignment per city,
economy rates (one coherent set), research target, army-group target, movement
target per unit, mission lifecycle per mission.

=== 3.6 Layer 5 — execution adapter

A thin `AIActions` interface wrapping the engine mutators (`moveUnit`,
`combatUnit`, `loadFerry`, `unloadFerry`, `setResearch`, `unitFortify`,
`rushCityProduction`, ...). Executors are the *only* code allowed to mutate the
engine. This removes the state-writing sprawl currently spread over ~17 unit
underscore fields and the `turnData` keys.

=== 3.7 Per-turn flow

[source]
----
WorldView
   -> SituationReport
      -> SituationDirector (select governors)
         -> active blocks propose
            -> arbiter (constraints + hysteresis)
               -> executors
                  -> decision log
----

=== 3.8 Shared state

One versioned `AIBlackboard` per civ, persisted under a single
`PlayerTurnStorage.turnData` key:

[source,typescript]
----
interface AIBlackboard {
  version: 2;
  situation: SituationReport;
  governors: GovernorSpec[];
  plans: Record<string, PlanState>;      // offensive plans, fronts
  missions: Record<string, MissionState>; // colony, invasion, ...
  decisions: DecisionLogEntry[];         // capped ring buffer
}
----

Missions keep their state-machine shape but gain one `Mission` interface, so
new types (blockade, convoy, escort) plug in instead of being bolted onto
`AIManager`.

== 4. Worked example — the naval case

* **Full naval war** — situation `posture: offensive`, geography
  `archipelago`, opportunity `seaInvasionTarget`. `NavalGovernor` activates
  `Blockade`, `FleetProduction` (warships), `NavalResearch`, `CoastalDefense`;
  land blocks are damped.
* **Island war** — `geography: small_island`, `threat.kind: landing`.
  `IslandDefenseGovernor` and `NavalGovernor` stack: `Escort`, `Beachhead`,
  `RaidResponse`.
* **Island invasion** — at war plus `seaInvasionTarget`.
  `NavalInvasion` (the existing `gather -> sail -> siege` state machine as a
  block) plus `FleetProduction` (ferry first). The current uncommitted naval
  work becomes one block instead of private `AIManager` methods.
* **Invaded by small groups** — `threat.kind: raid`. `RaidResponse` recalls
  the nearest one or two units and builds local defenders; it does *not*
  cancel the offensive plan or mobilise every garrison.
* **Auto production / tile adjustment / money / movement** are simply the
  `production`, `labor`, `economy`, `military` domains of the same machinery.

== 5. Migration plan

Each phase is independently shippable and keeps `npm test` green.

. **Phase 0 — shared kernel (no behaviour change).** Extract `WorldView`,
  shared predicates (`estimateUnitStrength`, `cityIsUnhappy`,
  `foodEmergency`, one `sustainableUnits`), one difficulty table, and a
  `DecisionLog`. Fix the dead knobs (`isBorderCity`, `AI_MIN_GOLD_RESERVE`,
  `shouldBuildOverUnit` receiving an offence-only count). This removes most
  duplication by itself.
. **Phase 1 — characterisation first.** Lock current AI-vs-AI outcomes as
  golden sessions, reusing `scripts/run-naval-session.mjs` and
  `tests/ai/tmpNavalSession.test.ts`. No refactor before this.
. **Phase 2 — production arbitration.** Convert
  `determineProductionItem` into scored blocks behind a feature flag; the
  current precedence becomes hard constraints. A/B against the ladder.
. **Phase 3 — movement director.** Extract `chooseAITarget` into per-unit
  proposal slots (scout block, combat block, mission overrides, fortify
  fallback).
. **Phase 4 — missions out of `AIManager`.** Colony and invasion state
  machines become governor blocks behind one `Mission` interface. Add
  `RaidResponse` and `Blockade`.
. **Phase 5 — SituationDirector and governor registry.** Start with three
  governors (`Balanced`, `Naval`, `IslandDefense`) on `AI_VS_AI_NAVAL`,
  measure with the session scripts, then derive the remaining profiles.
. **Phase 6 — fix dynamic strategy precedence.** Identity is a weight
  baseline, situation is a weight modifier — not a hard switch. Delete the
  unused `AIState` fields and the `resolveAICivStrategy` override.

=== 5.1 Verification per phase

* `npm run type-check`, `npm test`, `npm run lint`.
* Headless sessions: attacks per round, cities captured, techs per civ,
  survival rounds, disband churn (the `744 disband events` symptom from
  `doc/AI_VS_AI_ANALYSIS.md`).
* New decision-log assertions, e.g. "invasion mission created within N rounds
  of declaring war", "a small raid is answered by at most two units".

== 6. Strengths and weaknesses of this plan

=== 6.1 Strengths

* Situations become data: testable, observable, loggable.
* Blocks are pure and reusable across civs, governors, and map types.
* Governors emerge from composition instead of being hand-authored one by one.
* Every action is explainable (score + reason), which makes an AI this large
  debuggable.
* Fixes the concrete defects found in section 1 (dead dynamic strategy,
  duplicated predicates, ordering-as-policy).
* Incremental migration; existing tests remain the safety net.

=== 6.2 Weaknesses and risks

[cols="1,2",options="header"]
|===
| Risk | Mitigation
| Oscillation / decision thrash (classic utility-AI failure) | Hysteresis, commitment windows, bounded randomness (as `AIAggression` already does)
| Weight tuning becomes the maintenance burden | Headless batch harness plus decision-log diffs; never tune by intuition
| Combinatorial block interactions | One idea per block; hard rules stay explicit constraints, not emergent from weights
| Extracting a 4,454-line file is risky | Characterisation tests (Phase 1) are mandatory before any extraction
| Current uncommitted naval work moves the target | Commit and stabilise it before Phase 3-4
| "Fully dynamic" governors are hard to reproduce | Keep blocks hand-authored; only selection and weights are dynamic
| Performance (proposals per city per turn) | Blocks are pure and cached; scale is small (6 civs, tens of units)
|===

=== 6.3 A nuance on the original framing

A governor invented at runtime from arbitrary blocks is very hard to tune and
reproduce. The ideal is a hybrid of three stable layers:

* **Identity** (who am I) — profile and personality, stable, hand-authored.
* **Situation** (what is happening) — computed each turn.
* **Policy mix** (how do I respond) — blocks selected and weighted from
  identity plus situation.

Blocks stay hand-authored; only composition is dynamic.

== 7. Alternatives considered and rejected

* **Behaviour trees.** Good for unit micro, cannot express global economy
  coupling or scoring; poor explanation.
* **GOAP / HTN.** Powerful for goal sequencing, overkill for per-city
  production. At most usable for invasion mission sequencing.
* **Bigger FSM.** Cannot handle overlays such as "island-defending while
  invading"; this is essentially the current implicit approach.
* **Utility arbitration plus blackboard.** Chosen: handles overlays, supports
  scoring and explanation, and matches the existing proto-blocks
  (`AICoordinator`, `AIAggression`, the profiles).

== 8. Open questions

* Should the arbiter own per-unit movement, or should a separate "front"
  abstraction own army groups and only hand targets to units? (Phase 3
  decision.)
* How much randomness is acceptable in `RaidResponse` so behaviour stays
  varied without thrashing?
* Do governors need to react mid-turn (event-driven) or is once-per-turn
  sufficient? Today war declarations and city captures can fire events.
