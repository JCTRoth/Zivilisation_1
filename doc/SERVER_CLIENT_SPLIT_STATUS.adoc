== Executive summary

The headless simulation has been moved out of the browser into a three-package npm workspace. All five blockers from the original plan are closed, and every follow-up discovered during the work (transport, authentication, room lifecycle, client projection) has been implemented and tested.

The authoritative server can now create rooms from lobby settings, accept commands over HTTP or WebSocket, classify and fog-filter outbound events, persist/restore full game state including the RNG stream, and serve snapshots to a client that runs a read-only mirror engine. The browser can join such a room with a URL and keeps its entire read path unchanged — components still talk to a `GameEngine` instance and `sendCommand()`; only the transport behind the session differs.

The single failing test and the single lint warning in the suite are pre-existing and were reproduced on an untouched baseline worktree before any changes. No new failures were introduced.

== Closed tasks

=== 0. Package structure

* Converted the single-package Vite app into npm workspaces (`workspaces: ["packages/*"]`).
* Moved 285 files with `git mv` so history is preserved; deleted four dead legacy files (`game/City.ts`, `Civilization.ts`, `Unit.ts`, `Terrain.ts`) that had no importers.
* Rewrote 1,181 import specifiers with a codemod that resolved old paths against the pre-move tree and emitted relative aliases (`@shared/...`, `@/...`) per target package.
* Moved `index.html` into `packages/web/`; Vite uses `root: packages/web` and serves the root `public/` directory unchanged.
* Added `gameRuntime.ts` — the browser implementation of the presentation port (store-backed speed/handoff settings, camera glide, animation sleeps, toasts). `App.tsx` injects it into `new GameEngine(actions, webRuntime)`.
* Added a barrel `packages/shared/index.ts` exporting `GameEngine`, the runtime/saveStore ports, command types and `GameSettings`.

*Verification:* `npm run type-check`, `npm run build`, full suite.

=== 1. Determinism — one engine RNG

* `packages/shared/game/engine/Rng.ts` defines a stateful `Rng` interface (`mulberry32` with `getState`/`setState`), `createGameplayRng` with a salt distinct from map generation, and `rngInt`/`rngPick` helpers.
* `GameEngine` owns `rng` with `setRng()`, `seedRng()` and a new `GameSettings.rngSeed`. Without a seed it wraps the ambient `Math.random`, so legacy test fixtures and browser games behave exactly as before.
* Every gameplay roll is routed through it: combat contexts now pass `random: this.rng`; village outcomes, capture/building loss, tech picks, diplomacy/espionage, AI exploration and aggression, nomad decisions, disasters, auto-production and nuclear melt-downs all use the engine stream.
* `?seed=` in the web app and `LobbyConfig.seed` in the server set both `mapSeed` and `rngSeed`.
* Added `tests/determinism.test.ts`: stream equality, combat using the engine RNG rather than the global one, replay from the same seed, deterministic IDs, and tick deadlines.

*Acceptance criterion met:* same seed + same command sequence → same state.

=== 2. Deterministic IDs

* `GameEngine.nextId(prefix)` is a per-engine counter with collision skipping after a save load.
* `TurnManager` uses it for `u_1`, `u_2`, …; `AICoordinator` builds army ids from round + first unit id. Visual-only ids (glide animations, toasts, store request ids) were deliberately left wall-clock/random.

=== 3. Storage port

* `packages/shared/ports/saveStore.ts` defines `SaveStore { get, set }`, `browserSaveStore` (defensive `globalThis.localStorage`) and `createMemorySaveStore()`.
* `GameEngine.saveGame/loadGame` no longer reference `localStorage`; the constructor takes a third optional `SaveStore` argument.
* The server's `InMemorySaveStore` implements the shared interface and is injected by `GameRoom`. The v4/v5 blob and v1–v4 migrations are unchanged.

=== 4. Timers → simulation ticks

* `GameEngine` has a simulation clock: `currentTick`, `enableTickClock()`, `usesTickClock`, `scheduleTickDeadline()`, `ticksFor()`, `advanceTick()`.
* All six `DEFEATED_UNIT_REMOVAL_DELAY_MS` `setTimeout`s became `scheduleCorpseRemoval()` deadlines; browser keeps wall-clock, server uses ticks. `defeatTimestamp` stores sim ticks when tick-driven.
* `GameEngine.sleep()` resolves on tick deadlines in server mode (AI turn pacing, inter-move delays). A tick-driven engine must be advanced by its owner — `GameRoom` does this every `TICK_MS` (100 ms).
* The AI-turn watchdog in `TurnManager` is a tick deadline when the room is tick-driven, a wall-clock `setTimeout` in the browser. The only remaining wall-clock timer in shared code is a 3 s debug reminder when a human never registers — it changes no state.

=== 5. Command layer

* `packages/shared/types/commands.ts` defines 27 command types, a `CommandContext { actorId, turn, seq }`, typed results and machine-readable rejections.
* `GameEngine.submit(command, context)` enforces the turn gate and subject ownership, then delegates to the existing rules methods. Direct engine mutations are documented as engine-internal/AI/test-only.
* All UI mutation call sites were routed through `sendCommand()` (40 call sites across `GameCanvas.tsx`, `GameModals.tsx`, `CityModal.tsx`, `CityModalLogic.ts`, `SidePanel.tsx`, `RatesModal.tsx`, `App.tsx`). This includes specialist conversion, research, unit orders, improvements, diplomacy, trade routes and the production queue.
* Two deliberate exceptions remain, both documented in code: `EngineEventHandlers.advanceResearchPath` (event-driven AI-seat automation that would fail the seat-bound gate) and `MoveAnimator` (animation executor with a narrow `MoveEngine` interface).

*Verification:* `tests/commandLayer.test.ts` covers ownership/turn rejection and success paths, including the new command families.

=== Follow-up: RNG state in saves

* Save blobs now carry `rngState` and `disasterRngState` (still format version 5; older saves remain loadable). `loadGame` installs a stateful PRNG before restoring the saved position. DisasterManager exposes `getRngState`/`setRngState`.
* Test: save → draw 8 numbers → load → draw 8 numbers → identical.

=== Follow-up: authoritative server transport

* `classify.ts` maps engine events to wire events with `scope = universal | seat | location`, owning seat and map location; has an explicit rule table plus heuristic fallback.
* `fog.ts` implements `engineFogFilter(engine)` using the engine's own `isVisibleToPlayer`; `passAllFilter` remains for development.
* `GameRoom` sets `engine.onStateChange` to classify once and expose `addListener()`; it owns one engine, one tick loop and one save store.
* `RoomManager` handles create/add/get/list/remove/closeAll with sequential room ids.
* `HttpTransport` endpoints:

[cols="1,3"]
|===
|`GET /health` |server health and room list
|`POST /rooms` |create + start a room from a `LobbyConfig`; returns `{ id, token }`
|`GET /rooms` |list rooms
|`DELETE /rooms/:id` |stop and remove a room
|`POST /rooms/:id/commands` |`{ seat, token, command }` → `CommandResult`
|`GET /rooms/:id/events?token=…` |SSE stream of classified, fog-filtered events
|`GET /rooms/:id/state?token=…` |full save-blob snapshot for client mirrors
|`POST /rooms/:id/save`, `POST /rooms/:id/load` |persistence endpoints
|===

* `WsTransport` (`ws` + `@types/ws` added): same room registry, token-based join, command messages with `requestId`, filtered event pushes.

=== Follow-up: authentication

* `auth.ts` issues HMAC-SHA256 signed tokens (`createSeatToken`, `verifySeatToken`, `tokenSeatResolver`) bound to room id and expiry, verified with `timingSafeEqual`.
* When a transport is configured with `secret`, the token is authoritative: a forged `seat` field in a command body or query string is ignored. Without a secret the transports keep the demo `?seat=` behaviour.

=== Follow-up: client transport and remote mode

* `remoteSession.ts` implements `GameSession` over HTTP POST with optional `onResult` refresh hook.
* `remoteEvents.ts` consumes SSE frames with reconnectable `close()` and an `onConnected` hook.
* `OutboundEvent` lives in shared `types/events.ts` so the client does not import server code.
* `remoteGame.ts` creates a read-only mirror `GameEngine` with a memory save store, binds the remote session, loads snapshots through `loadGame()`, refreshes on replies/events (coalesced), and exposes `refresh()`/`close()`.
* `session.ts` exports `hasActiveSession()`; `UseGameEngine` will not replace an already-bound remote session.
* `App.tsx` joins a room from `?server=…&room=…&token=…[&seat=…]` and closes the stream on unmount.

== Open tasks and known limitations

1. *Snapshot refresh granularity.* Remote mode fetches and reloads a full save blob whenever a command reply or event burst arrives. Correct, but chattier than an incremental projection; large games may notice the cost.
2. *Lobby UI.* Room creation/join is available through `POST /rooms` and URL parameters, but there is no in-app lobby screen for selecting seats, inviting players or displaying tokens.
3. *Seat assignment.* Tokens are signed, but the server issues only the host (seat 0) token in `POST /rooms`. A real lobby must mint one token per seat and deliver it securely.
4. *Event projection.* The mirror engine is refreshed via snapshots; `subscribeToRoomEvents` is used only as a refresh trigger. The event payloads are not yet applied incrementally to the Zustand projection independently of `loadGame()`.
5. *Engine event surface.* Some engine events still carry whole objects (units, cities); a fine-grained client reducer would need a stable event schema.
6. *Pre-existing test/lint issues* listed above remain untouched by design.
7. *Persistence backend.* `InMemorySaveStore` is room-local; there is no database-backed `SaveStore` for reconnect/restart survival.
