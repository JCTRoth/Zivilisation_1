= Round Manager and Automated Path Following Implementation

== Overview

**Round management now lives in `src/game/engine/TurnManager.ts`.** The
original `src/game/engine/RoundManager.ts` was merged into it and no longer
exists; the only trace of the old name is a comment — `TurnManager.ts:181`,
`// --- Unit path management (compatibility with previous RoundManager) ---`
— and a few stale code comments elsewhere. Nothing in the repository logs
with the `[RoundManager]` prefix any more.

This document describes the system as it is today: the real API, the legacy
`roundManager` property that kept its name, the log prefix to filter on, and
how automated path following fits into the turn flow.

== Components

=== 1. TurnManager (`src/game/engine/TurnManager.ts`)

*Purpose*: runs the turn for every civilization — phase machine, unit turn
queue, AI turns, research/production phases — **and** owns the unit path
store that used to belong to `RoundManager`.

*Unit path API* (the old RoundManager surface, kept for compatibility —
`TurnManager.ts:182-196`):

[source,typescript]
----
setUnitPath(unitId, path)                 // TurnManager.ts:182 — store a path
getUnitPath(unitId)                       // TurnManager.ts:186 — read it back
clearUnitPath(unitId)                     // TurnManager.ts:189 — drop it
getAllUnitPaths()                         // TurnManager.ts:193 — copy of the map
cleanupDestroyedUnits(existingUnitIds)    // TurnManager.ts:196 — prune dead units
----

The store is a plain `Map<string, Array<{ col, row }>>` (`TurnManager.ts:44`),
created with the manager and cleared with it (`:82`, `:111`). Paths persist
across turns; they are what the UI and `GoToManager` read and write.

*Automated movement*:

[source,typescript]
----
processAutomatedMovements(civilizationId)   // TurnManager.ts:1614 (private)
----

Runs at the start of the `UNIT_MOVEMENT` phase (`TurnManager.ts:387`): every
unit of that civilization that still has a stored path and movement points
walks one step after another, the path shrinking with each successful move
and being cleared when a step fails or the destination is reached.

*Turn API* (what actually exists — there is **no** `executeCivilizationTurn`
and **no** `startNewRound`):

[source,typescript]
----
startTurn(civilizationId)   // TurnManager.ts:242 — reset moves, open the turn
endHumanTurn()              // TurnManager.ts:339 — the human's "End Turn"
nextPhase()                 // advance the phase machine
getRoundNumber() / restoreState(...) / getPhase()   // round bookkeeping + save
----

=== 2. GameEngine integration (`src/game/engine/GameEngine.ts`)

* The property is still called `roundManager`, but its type is `TurnManager`:
  `roundManager: TurnManager; // kept property name for compatibility`
  (`GameEngine.ts:330`), assigned `this.roundManager = new TurnManager(this)`
  (`:434`), and handed to `GoToManager` right after (`:435`).
* `GameEngine.processTurn()` (`:7144`) does nothing itself: it delegates to
  `this.roundManager.endHumanTurn()` (`:7158-7159`).
* The first turn is opened with `this.roundManager.startTurn(this.activePlayer)`
  (`GameEngine.ts:1211`).
* Save/load round-trips the paths through the alias:
  `this.roundManager.getAllUnitPaths()` in `getSaveJSON()` (`:9082`) and
  `setUnitPath` / `restoreState` when loading (`:9416`, `:9429`).

Turn flow as it runs today:

[source]
----
GameEngine.processTurn()                (GameEngine.ts:7144)
  └─► TurnManager.endHumanTurn()        (GameEngine.ts:7158)
        ├─ cleanup / advance to the next phase
        ├─ CITY_PRODUCTION → RESEARCH → END
        └─ startTurn(nextPlayer)  (TurnManager.ts:733)
              └─ UNIT_MOVEMENT phase:
                   processAutomatedMovements(civ)   (TurnManager.ts:387)
                     → walk stored GoTo paths, then the unit turn queue
----

=== 3. GameCanvas integration (`src/components/game/GameCanvas.tsx`)

* On every turn change the canvas reloads the paths for the UI:
  `roundManager.getAllUnitPaths()` (`GameCanvas.tsx:1125-1129`, behind the
  `Sync unit paths … on turn change` effect).
* Orders go through `GoToManager` (`calculatePath` / `setUnitPath` /
  `getUnitPath` / `clearUnitPath`, `GameCanvas.tsx:1998-2081`), which writes
  into the same store — its collaborator field is *named* `roundManager` but
  typed `TurnManager` (`GoToManager.ts:25,28`).

=== 4. SettlementEvaluator logging

The `SettlementEvaluator` logging notes that used to travel with this document
(`getTileYields`, `hasWaterAccess`, `evaluateArea`) are unchanged and live in
`src/game/engine/SettlementEvaluator.ts`.

== How it works

=== User workflow
. User selects a unit and clicks "Go To" from the context menu.
. User clicks the destination tile.
. The path is computed in `Pathfinding.ts` and stored through
  `GoToManager.setUnitPath` → `TurnManager.setUnitPath`.
. The unit moves the first step immediately if it still has moves; the route
  is drawn as a red line with an arrow.
. On the next turn the `UNIT_MOVEMENT` phase picks the path up again.

=== Path persistence
* Paths live on the engine level (`TurnManager.unitPaths`), so they survive
  turn changes and save/load.
* They are synced to `GameCanvas` for display, and shown only for the
  selected unit.
* Cleared when the unit reaches its destination, when a step fails, when the
  order is cancelled — or explicitly by `cleanupDestroyedUnits(existingUnitIds)`
  (`TurnManager.ts:196`). Note that neither that method nor its `GoToManager`
  twin (`GoToManager.ts:345`) has a caller in `src/` today, so a destroyed
  unit's path is currently left in the map until something clears it.

== Logging

Every major operation is logged with the **`[TurnManager]`** prefix — 80-plus
occurrences in `TurnManager.ts`, and *zero* `[RoundManager]` occurrences in
`src/` or `tests/`:

[source,javascript]
----
// Filter TurnManager logs in the browser console
console.log = (function(log) {
  return function() {
    if (arguments[0] && arguments[0].includes('[TurnManager]')) {
      log.apply(console, arguments);
    }
  };
})(console.log);
----

== Testing recommendations

. *Basic path following*: set a path, end the turn, verify the unit moves.
. *Multiple units*: several paths, each followed independently.
. *Blocked paths*: a path that becomes impassable is cleared, not retried.
. *Turn changes*: paths persist and continue across turns.
. *Unit destruction*: the path does not outlive its unit.
. *Save/load*: paths survive a round trip (`getSaveJSON` → `loadGame`).
