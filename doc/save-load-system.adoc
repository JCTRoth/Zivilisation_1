= Save & Load System — Diplomacy & Game Menu Features

:toc:
:toclevels: 2
:sectnums:

This document describes the Save/Load game system and the leader portrait rendering used by the diplomacy and audience dialogs in Civilization I Browser Game.

== Save / Load System

:toc:
:toclevels: 2
:sectnums:

The game supports saving and loading the complete game state. Saves live in a
*campaign library* on the player's device, can be exported to a `.json` file
and imported back, and are fully available with or without a network
connection.

The full design — and the reasons behind it — are in
link:OFFLINE_PWA_PLAN.adoc[Offline Play & PWA — Implementation Plan].

=== Architecture

Three layers, each with one owner:

[cols="1,3"]
|===
|Layer |Owner

|Storage port
|`packages/shared/ports/saveStore.ts` — the engine's synchronous `{ get, set }` slot API. Unchanged; the engine never touches `localStorage` or IndexedDB directly.

|Campaign library
|`packages/shared/ports/campaignStore.ts` — the asynchronous `{ list, read, write, remove }` port for a browsable list of named campaigns. `packages/web/src/pwa/indexedDbCampaignStore.ts` implements it against IndexedDB.

|Browser facade
|`packages/web/src/pwa/browserSaveStore.ts` — a synchronous `SaveStore` backed by an in-memory map that writes through to IndexedDB (or to `localStorage` when IndexedDB is unavailable). The engine sees exactly the same API it always saw.

|===

Because the facade keeps a synchronous in-memory map, `GameEngine.saveGame()`
and `GameEngine.loadGame()` work unchanged — and the server, which writes to
SQLite through the same port, is unaffected.

=== The campaign library

A *campaign* is one named entry in the library:

[source,json]
----
{
  "id": "campaign-l3k9x2",
  "name": "Rome — saved",
  "turn": 42,
  "year": -1200,
  "civilizationName": "Rome",
  "updatedAt": 1763654321000,
  "sizeBytes": 2718344,
  "version": 5,
  "kind": "manual"
}
----

* **Where it lives.** IndexedDB, database `civ1`, object store `campaigns`,
  keyed by `id`. When IndexedDB is unavailable (private mode, a locked-down
  kiosk) the store falls back to `localStorage` and says so in the console.
  A device that is out of space also steps down to `localStorage`; the player
  is told with a toast that saves are now limited.
* **When it is written.** A deliberate save (the manual slot, a named
  campaign) reaches the disk immediately — the player may close the tab right
  afterwards. The end-of-turn autosave is debounced. The store also flushes
  when the tab is hidden or closed.
* **The engine's own slots.** `civ1_savegame` (manual) and `civ1_autosave`
  (written at the end of every turn) are campaigns too, with `kind`
  `manual` / `autosave`.
* **Migration.** A legacy `localStorage` save is imported on the first
  launch. The legacy key is deleted only *after* the campaign is safely in
  the library, so a failed write never destroys the only copy.

=== Save Game (File Download)

When the player clicks **Save Game** in the GAME menu:

. `gameEngine.getSaveJSON()` serializes the complete game state to JSON.
. The blob is written into the campaign library under the manual slot
  `civ1_savegame` — so the game can be continued later, offline.
. The same JSON is handed to the browser as a download through a temporary
  `<a download>` element; the file name follows the pattern
  `civ1-save-turn-{turn}.json`.

On success a notification *"Game saved to civ1-save-turn-{n}.json"* is shown.

=== Load Game (File Picker)

When the player clicks **Load Game**:

. The native file picker opens, filtered to `.json`.
. The file is read with `file.text()` and validated against the shared
  version contract (`packages/shared/types/saves.ts`).
. The blob is added to the campaign library under the manual slot.
. `gameEngine.loadGame()` restores the state; the UI then forces a full
  store sync (map, units, cities, civilizations, technologies, visibility).

A cancelled picker changes nothing.

=== The Campaign Library

`GAME ▸ Campaigns` opens a panel over the running game. The pre-game wizard
has no library or *Continue* card: saving stays inside the game.

* **Continue** — restore a campaign, replacing the current game in place.
  From the setup wizard, start a game first and use `Ctrl+L` or `GAME ▸ Load Game`.
* **Save current game** — write the running game into the library under a
  name of the player's choosing.
* **Export** — download a campaign as a `.json` file (the raw V5 blob).
* **Import from file** — read a `.json` file and add it to the library.
* **Delete** — remove a campaign from the device.

The panel works with no network: the library is on the device.

=== Keyboard Shortcuts

* `Ctrl+S` — save the manual slot (and toast *"Game saved locally."*).
* `Ctrl+L` — load the manual slot (and toast *"Game loaded from the local
  save."*).

Both are handled in `App.tsx`'s keydown handler.

=== Save File Format

Save files are plain JSON with the following structure:

[source,json]
----
{
  "version": 5,
  "timestamp": 1717539200000,
  "gameSettings": {
    "fixedAlliances": true,
    "teamAssignments": [0, 0, 1],
    ...
  },
  "currentTurn": 42,
  "currentYear": -3200,
  "activePlayer": 0,
  "map": {
    "width": 50,
    "height": 40,
    "tiles": [ ... ],
    "visibility": [ ... ],
    "revealed": [ ... ]
  },
  "units": [ ... ],
  "cities": [ ... ],
  "civilizations": [ { "id": 0, "teamId": 0, ... }, ... ],
  "technologies": [ ... ]
}
----

=== Save format versions

[cols="1,3", options="header"]
|===
|Version |Changes

|1
|Initial format.

|2–4
|Earlier diplomacy/economy additions. No team fields.

|5
|Fixed alliances: `gameSettings.fixedAlliances`, `gameSettings.teamAssignments` and `civilizations[].teamId`.
|===

Versions 1–4 load as free-for-all. A version-5 save with
`fixedAlliances: false` (or an invalid team assignment) also loads as
free-for-all. See link:FIXED_ALLIANCES.adoc[Fixed Alliances].

[NOTE]
====
The version gate now lives in exactly one place:
`isSupportedSaveVersion()` in `packages/shared/types/saves.ts`. The engine's
`loadGame()` and the file picker both call it, so they can no longer drift
apart.

This fixed a long-standing bug: the picker used to accept versions 1–3 while
the engine wrote version 5, which meant *a save written by this build could
not be loaded back through the menu*. Known limitation as of 2026-11-07,
fixed as of 2026-11-20.
====

=== Offline behaviour

* Single-player saves and loads without any server: the campaign library is
  on the device.
* The file export and import work without a network — the browser's file
  picker and download are local operations.
* A multiplayer room keeps its state on the server. Its client-side mirror
  is not part of the local campaign library.

[[save-load-limitations]]
=== Limitations

* No cloud save support: campaigns live on the device and travel only as
  exported files.
* Large maps with many units produce save files of several megabytes. The
  library therefore uses IndexedDB rather than `localStorage`, whose ~5 MB
  per-origin quota would otherwise be the ceiling.
* A browser that blocks IndexedDB falls back to `localStorage`, which brings
  the size ceiling back. The game keeps running; only the size of a save is
  limited.
* A save written by a *newer* format version is rejected by both the engine
  and the file picker.

== Leader Portraits

The Diplomacy negotiation modal (`diplomacy` dialog) and the Audience dialog
(`audience`) display leader portraits for each civilization. There is no
`diplomacy-report` dialog any more — it was removed from the code (the
comment in `e2e/game.spec.ts` records the removal), and it used to be named
in this document, `doc/auto-end-turn.adoc` and `doc/MODALS.adoc`.

=== Architecture

Leader portraits are rendered by the `LeaderPortrait` React component (`src/components/ui/LeaderPortrait.tsx`).

The component supports two rendering modes:

1. **Image mode** (preferred):::
   If a `leaderName` prop is provided and a matching JPG file exists in `src/assets/leader/`, the component renders an `<img>` element pointing to the imported image asset. This is the primary rendering path.

2. **Procedural SVG mode** (fallback):::
   If no `leaderName` prop is provided (or no matching image is found), the component falls back to generating an SVG portrait procedurally from the `LeaderPortraitConfig` data defined in `src/data/LeaderPortraits.ts`.

Images are imported in `LeaderPortrait.tsx` via Vite's static asset import:

[source,typescript]
----
import leader_Alexander_the_Great from '@/assets/leader/Alexander_the_Great.jpg';
import leader_Elizabeth_I from '@/assets/leader/Elizabeth_I.jpg';
// ... etc.

const LEADER_IMAGES: Record<string, string> = {
  'Alexander the Great': leader_Alexander_the_Great,
  'Elizabeth I': leader_Elizabeth_I,
  // ... etc.
};
----

=== How It Works

When rendering a leader portrait:

1. The caller (e.g., `GameModals.tsx`) looks up the leader name from the civilization data (e.g., `civ.leader` or `civ.leaderName`)
2. It finds the matching `LeaderPortraitConfig` from `LEADER_PORTRAITS` in `src/data/LeaderPortraits.ts`
3. It passes `config`, `mood`, `size`, and `leaderName` props to the `LeaderPortrait` component
4. The component checks if `leaderName` matches a key in `LEADER_IMAGES` — if so, it renders the JPG image; otherwise it renders the procedural SVG

The `leaderName` prop is the key that activates image mode. Without it, the component defaults to SVG rendering. The main Diplomacy modal and the Audience dialog both pass this prop.

=== Mood-Based Visual Feedback

The portrait frame and background reflect the AI's attitude:

* **Friendly** — Green glow (`#1a2e1a` background, `#4caf50` border)
* **Neutral** — Blue-gray (`#1a1a2e` background, `#8b7355` border)
* **Annoyed** — Orange glow (`#2e2a1a` background, `#ff9800` border)
* **Hostile** — Red glow (`#2e1a1a` background, `#f44336` border)

This applies to both the image and SVG rendering modes.
